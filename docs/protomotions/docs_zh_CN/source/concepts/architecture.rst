架构概述
========

ProtoMotions 围绕模块化组件设计，这些组件可以自由组合搭配，构建不同的训练场景。

高层数据流
----------

.. code-block:: text

   ┌─────────────┐     ┌─────────────┐
   │   Terrain   │     │ Scene Lib   │
   └──────┬──────┘     └──────┬──────┘
          │                   │
          └────────┬──────────┘
                   ▼
   ┌─────────────────────────────┐
   │        Simulator            │
   │(IsaacGym/Lab/Newton/Gen/MJ)│◄─── Robot Config
   └──────────────┬──────────────┘
                  │
                  ▼ SimulatorState
   ┌─────────────────────────────┐
   │      RL Environment         │◄─── Motion Library
   │  (observations, rewards)    │
   └──────────────┬──────────────┘
                  │
                  ▼
   ┌─────────────────────────────┐
   │          Agent              │
   │   (policy, value, update)   │
   └─────────────────────────────┘

组件职责
--------

**Terrain（地形）**：程序化生成高度场，为仿真提供地面。

**SceneLib**：物体的生成与管理，在场景中创建障碍物、道具和可交互物体。

**Robot Config（机器人配置）**：定义"仿真什么角色"——身体映射、PD 增益、物理设置。
MJCF 文件是基准真值，配置文件在此基础上补充仿真器特定的细节。

**Simulator（仿真器）**：物理引擎抽象。所有后端（IsaacGym、IsaacLab、Newton、
Genesis、MuJoCo）都实现同一接口。这解决了"如何仿真"的问题。

**Motion Library（动作库）**：将参考动作存储为打包张量，支持高效的并行访问。

**RL Environment（强化学习环境）**：通过模块化组件编排训练循环：

* **控制组件**：有状态的任务管理器（mimic、steering、path following）
* **观测组件**：计算观测的无状态函数
* **奖励组件**：计算奖励的无状态函数
* **终止组件**：检查终止条件的无状态函数

**Agent（智能体）**：强化学习算法（PPO、AMP 等），负责收集经验并更新策略。

为什么这样设计？
----------------

**问题**：我们需要支持大量组合：

* 5 个仿真器 × N 种机器人 × M 种算法 × K 种环境

如果没有抽象，就需要 N×M×K 套独立的实现。

**解决方案**：在组件之间定义清晰的接口：

* 各仿真器共享 ``SimulatorState`` 状态表示
* 环境产出 ``TensorDict`` 观测
* 智能体消费观测、产出动作
* 机器人配置与仿真器无关
