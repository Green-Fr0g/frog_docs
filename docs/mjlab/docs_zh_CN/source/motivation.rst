.. _motivation:

为什么选择 mjlab？
==================

强化学习已经成为在仿真中训练机器人控制器并将其迁移到真实硬件的强大工具。
这条流程的效果好坏，取决于仿真细节是否处理得当。

有多个框架都在解决这个问题。
`Isaac Lab <https://github.com/isaac-sim/IsaacLab>`_
提供了一套全面的、基于管理器的 API 来组合 RL 环境，但它依赖 Omniverse
运行时，增加了安装复杂度和启动延迟。
`MuJoCo Playground <https://playground.mujoco.org/>`_ 则走相反的路线：
抽象极少，环境定义是单体式的，便于随意修改、原型迭代快，但跨机器人和任务的
代码重复使多任务代码库难以维护。尽管如此，仍然缺少这样一个框架：既足够轻量，
又构建在经过验证的编排式 API 之上，并能使用一流的物理引擎。

mjlab 填补了这一空白。它采用 Isaac Lab 基于管理器的设计——用户把观测、
奖励、事件和指令组合成自包含的构建块——并与 MuJoCo Warp 搭配，实现
GPU 加速的物理仿真。其结果是一个依赖极少、启动迅速、可直接访问原生
MuJoCo 模型和数据结构、并为策略训练提供 PyTorch 原生接口的框架。


设计哲学
--------

mjlab 围绕三项核心工程承诺设计：

1. **安装门槛极低。** 一条 ``uvx --from mjlab --refresh demo`` 命令
   即可运行框架。没有重量级运行时，也没有动辄数 GB 的下载。依赖足迹被
   刻意保持在很小的规模。

2. **透明、可审查的物理。** mjlab 只针对单一物理栈——MuJoCo Warp——
   以优先保证仿真的透明性和可调试性。框架直接暴露 MuJoCo 原生的
   ``MjModel`` 和 ``MjData`` 结构，便于直接检查和访问状态。跨仿真器
   可移植性并非目标；相比后端通用性，mjlab 更看重精确的控制和可解释性。

3. **与 MuJoCo 生态深度集成。** 用户直接使用 MuJoCo 的模型和约定。
   MJCF 文件、MuJoCo Menagerie 资产以及标准 MuJoCo 工具链都无需任何
   翻译层即可使用。


适用范围
--------

mjlab 为刚体机器人学习提供基础设施，包含用于几何感知的深度和射线投射
传感器。高保真 RGB 渲染不在范围内。但这并不妨碍基于视觉的策略：一种
常见做法是先用全量状态训练特权策略，再借助外部渲染将其蒸馏为基于视觉的
控制器。

该框架旨在支持对自定义机器人、任务、传感器和执行器的扩展。它附带速度
跟踪、动作模仿和操作任务的参考实现。


对比
----

.. list-table::
   :header-rows: 1
   :widths: 25 25 50

   * - 框架
     - 优势
     - 适用场景
   * - **mjlab**
     - 轻量、迭代快、原生 MuJoCo、PyTorch
     - 希望获得带 GPU 加速的结构化 RL 环境的 MuJoCo 用户
   * - **Isaac Lab**
     - 照片级渲染、USD 流程、Omniverse 生态
     - 需要 Isaac Sim 能力的项目
   * - **MuJoCo Playground**
     - 抽象极少、易于修改、原型迭代快
     - 一次性实验和单任务的快速迭代
   * - **Newton**
     - 多物理求解器（可变形体、VBD）、可微仿真
     - 需要超出刚体 MuJoCo 的求解器灵活性的项目
